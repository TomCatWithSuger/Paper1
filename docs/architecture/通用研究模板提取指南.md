# 通用深度学习研究实验模板提取指南

## 1. 用途与范围

本文用于从 Paper1 提取一个独立的通用神经网络研究仓库，指导移除论文业务、保留实验基础设施，并为今后的模型研究、算法对比和实验分析建立约定。

目标定位：**General-Purpose Deep Learning Research Template，通用深度学习研究实验模板**。

这不是新的 PyTorch 或 Lightning 框架，也不是预先实现所有模型的算法库。它应允许研究者增加 Network、Method、数据和指标，而不必为每个实验重建训练、配置、测试与结果管理流程。

**本文是提取规格，不表示新仓库已经创建。** 当前 Paper1 的实际架构见[模型结构说明](src_models%E7%BB%93%E6%9E%84%E8%AF%B4%E6%98%8E.md)。本文的“目标结构”“验收要求”属于后续工作，不能视为当前全部已有的能力。

模块应如何划分、依赖如何组装与检查、AI 如何接入新实验，以及文件长度/注释/CI 规则，以[研究模板开发规范](%E7%A0%94%E7%A9%B6%E6%A8%A1%E6%9D%BF%E5%BC%80%E5%8F%91%E8%A7%84%E8%8C%83.md)为准。提取时应同步迁移规则和 Skill，并实际接入门禁；只有目录结构和文档还不足以保证开发体验。

提取应在新仓库或独立副本中进行，不直接清空 Paper1；历史权重、日志、研究报告和实验产物继续留在原项目。

## 2. “去除实现逻辑”的边界

建议去除的是具体论文和任务绑定，不是去掉所有能够运行的实现。

| 层次         | 处理原则                           | 示例                                                  |
| ------------ | ---------------------------------- | ----------------------------------------------------- |
| 模板基础设施 | 保留并去除业务绑定                 | 训练/评估入口、Hydra 组装、日志、优化器构造、测试工具 |
| 通用能力     | 有实际调用者或独立测试价值才保留   | 数值积分、掩码损失、学习率调度                        |
| 最小示例     | 至少保留一条完整、离线可运行的路径 | 合成数据、小型 MLP、分类目标、训练和恢复              |
| 可选研究示例 | 按需要保留，不作为默认依赖         | Flow Matching、GAN、AE、DDPM                          |
| 论文业务     | 不迁入模板核心                     | B1/B2/B3 约定、MeanVC 特征、源身份诊断、声码器评估    |
| 实验产物     | 不随模板迁移                       | 数据缓存、预训练权重、历史检查点、音频、已有结果表    |

如果希望删除所有现有算法实现，可以重新提供一个最小监督学习示例；但不要只留下 `pass` 或 `NotImplementedError` 再宣称模板可用。

GAN 和 Flow 不必成为默认示例。选择删除时，应同步删除对应配置、测试和“已支持该算法”的说明；通用的参数角色、阶段语义和数学工具测试可按实际保留范围转为小型测试替身。

## 3. 建议目标结构

以下是新仓库的职责结构，不是要求一次性创建所有目录。只有存在实现或说明时才建立对应目录；文件名属于提议，不代表 Paper1 已存在。

```text
research-template/
├── README.md                         # 定位、离线首跑、扩展方式、支持边界
├── pyproject.toml                    # 依赖与测试配置
├── configs/
│   ├── train.yaml                    # 默认选择最小离线实验
│   ├── eval.yaml
│   ├── model/                        # 已验证的 Module/Method/Network 组合
│   ├── data/                         # 数据契约与具体数据配置
│   ├── experiment/                   # 基线、变体、消融配置
│   ├── trainer/
│   ├── callbacks/
│   ├── logger/
│   └── paths/                        # 可移植路径，禁止个人绝对路径
├── src/
│   ├── train.py
│   ├── eval.py
│   ├── data/                         # Dataset、DataModule、划分与预处理
│   ├── models/
│   │   ├── components/               # 可复用局部计算组件，按需建立
│   │   ├── networks/                 # 纯前向参数化函数
│   │   ├── methods/                  # 学习目标与算法流程
│   │   ├── modules/                  # Lightning 执行适配
│   │   └── algorithms/               # 可复用数学原语，按需保留
│   ├── losses/                       # 独立损失，按需保留
│   ├── optim/                        # 优化工具，按需保留
│   ├── analysis/                     # 实验记录、聚合与对比，按需实现
│   └── utils/                        # 小型公共工具，不存放业务杂项
├── tests/                            # 合成数据测试，不依赖本地语料
├── scripts/                          # 薄命令行入口，按需建立
├── docs/                             # 架构、实验协议、新实验接入步骤
└── .github/workflows/                # 与最小依赖和离线测试一致的 CI
```

保留现有单层嵌套模型配置，不立即拆出 network/method/module 配置组。也不预建 GNN、SSM、强化学习、自定义执行后端或通用阶段调度器。

运行产生的数据、日志、检查点和分析结果目录按需生成，默认忽略大文件；不要求作为模板版本库内容提交。

## 5. 新仓库必须保留的架构契约

### 5.1 四层职责

| 层级      | 负责                                         | 不负责                                 |
| --------- | -------------------------------------------- | -------------------------------------- |
| Component | 局部计算、局部参数和状态                     | 具体实验、Trainer 生命周期             |
| Network   | 明确输入输出的前向计算，可组合子网络         | 损失、监督目标、训练调度               |
| Method    | 目标、损失、扰动、生成、算法阶段和参数角色   | Lightning 日志、Trainer 访问、框架反传 |
| Module    | Batch 适配、执行、指标、优化器、调度器和恢复 | 重新实现算法公式、访问具体网络内部层   |

依赖方向为 Module → Method → Network → Component。Method 可以持有条件编码组件并调用算法原语；数值原语不依赖具体 Method 或执行框架。

Method 和 Network 都可以独立用 PyTorch 运行。不强制所有网络使用同一个 `forward()`，也不为了抽象而增加万能 BaseModel。

### 5.2 组合与参数

- 可替换性以 Shape、轴顺序、条件/时间字段、Mask、输出数学语义和额外能力为准，不以类名或目录判断。
- 单网络 Method 可使用 `method.network`；多网络 Method 可以使用具名网络集合，不必强行包装成一个 `.network`。采用后者时必须同步调整执行器的 compile 和恢复接口，不能直接复用现有假设。
- Component、Network、Method 都可以持有 Parameter 和 Buffer；注册应有明确路径，Module 不另行注册重复网络引用。
- 参数共享与跨优化器共享是不同问题。共享网络参数必须明确更新与保存语义，不能无意复制；当前 GAN 的禁止跨角色共享是该示例限制，不是所有算法的统一限制。
- 算法要求的阶段顺序、频率、样本复用和梯度截断由 Method 或显式算法配置定义；Module 负责执行，不隐式改变算法。
- 冻结参数、停止梯度、不调用优化器和切换 train/eval 不是同一件事。测试应分别检查梯度、参数、Buffer 和随机状态。

### 5.3 训练返回值

不要求所有 Method 返回一个全局万能结果对象。为每类 Module 明确约定即可：损失是否为标量、是否包含分项、预测是什么、生成是否使用独立入口。

现有 `GenerativeModule.predict_step()` 取训练结果第二项；对某些算法这不是最终生成样本。保留它时必须说明语义，不能把所有 `predict` 自动称为生成。新实验应显式验证预测/生成输出。

### 5.4 检查点兼容

新模板默认不承担 Paper1 历史权重兼容。当前 `_map_legacy_state_dict()` 位于通用生命周期文件，且被 GAN 使用；移除兼容层时必须同步清理所有调用和导入，不能只删函数。

不要求迁移旧权重时，可以从新模板中移除旧 `net.*` 映射与历史专用恢复规则，直接按新仓库公开契约保存和加载。若保留旧权重支持，应明确支持版本，并增加真实键名和参数顺序测试。

“加载权重”“恢复训练状态”“精确续跑”须分别声明。只验证模型权重和优化器恢复，不能声称 RNG、DataLoader、Worker、数据游标和分布式状态全部精确恢复。

## 6. 最小可运行示例

新仓库默认入口应使用如下完整路径，建议以分类为首个示例：

```text
固定种子的合成数据
  → Dataset / DataModule
  → 小型 MLP Network
  → 分类 Method
  → 分类 Lightning Module
  → Hydra 实验配置
  → CPU 训练、验证、测试、预测与检查点恢复
```

验收重点是工程链路，不是分类分数高低。训练、验证和测试划分应可重复且互不混用；默认运行不请求网络、不读个人语料、不依赖预训练权重或 GPU。

所有生产模块应承担实际职责。只有一个调用者的简单实现可以留在所属文件，不强制为了凑四层创建空 Component。

若希望保留对生成和多网络训练的开箱支持，可再选小型 Flow 和 GAN 作为可选配置。只保留分类示例时，应将其他流程标为“扩展点”，不得继承 Paper1 对这些实现的测试结论。

## 7. 实验分析应形成的最小闭环

以下为新模板的目标约定。可以先通过结构化文件和一个聚合脚本实现，不需要数据库、仪表盘或复杂实验平台。

### 7.1 单次运行记录

每个运行应有独立 `run_id` 和输出目录，至少记录：

| 信息     | 内容                                                     |
| -------- | -------------------------------------------------------- |
| 配置     | 解析后的完整配置、命令行覆盖、配置身份                   |
| 代码     | 代码版本和是否存在未提交改动；无 Git 环境时明确标注      |
| 环境     | Python/关键包版本、设备、精度和确定性设置                |
| 数据     | 数据版本或清单身份、划分、预处理版本；路径不等于内容身份 |
| 随机性   | 训练种子、评估种子/重复次数、数据顺序设置                |
| 训练状态 | 成功/失败/中断、步数、训练时长及资源口径                 |
| 权重     | best/last/指定检查点、选择规则及其可核验身份             |
| 指标     | 名称、单位、越高/越低越好、split、聚合方式和缺失原因     |

默认日志器关闭时，也应明确哪些基础记录仍会保存；不要假定接入日志器才有运行身份。记录配置时不要写入令牌、密码等秘密。

### 7.2 对比与消融

- 以同一任务和评估协议为比较单位，记录数据划分与预算是否一致；不同预算可比较，但必须标明，不能当作严格受控消融。
- 区分独立训练种子与同一检查点的重复采样，不把后者伪装成多个独立训练实验。
- 记录每次运行的结果，再汇总均值、离散程度和有效运行数；失败运行不悄悄删除，未计算指标不填零。
- 以验证集选超参数和检查点，测试集用于最终报告；明确缺失、跳过和失败原因。
- 续写分析结果时校验配置、数据、检查点和评估协议身份；不把不同实验的结果接到同一个账本。
- 分析入口读取规范结果，不依赖具体 Network 的内部层；任务专用诊断仍由该任务提供。

这部分应作为新仓库的独立验收项。Paper1 已有任务级分析不等于上述通用记录和对比系统已完整实现。

## 8. 推荐提取顺序

1. 明确是否保留分类、Flow、GAN 示例，列出生产代码、配置、测试与依赖的保留清单。
2. 在独立仓库或副本操作，保留原项目；不复制数据、权重、运行日志、个人环境文件和秘密。
3. 先建立离线合成数据与模板级测试夹具，解除公共测试对语音模块的顶层依赖。
4. 调整默认训练/评估配置，使最小示例能完整运行；移除不保留实现的配置与参数化测试条目。
5. 按完整依赖关系移除论文实现、旧检查点兼容与任务分析；检查包初始化文件、延迟导入和字符串 `_target_`。
6. 精简依赖及相关 CI、安装说明和锁文件，保留上游来源与适用许可文件。依赖解析/下载需单独授权，不在本次文档工作中执行。
7. 实现最小运行记录和结果聚合，验证基线与一个配置变体可以被规范比较。
8. 运行下面的验收清单，重写 README 的支持范围和测试结论后再发布。

首次提取不同时升级所有依赖或重命名所有公开类；先建立可运行基线，再单独处理兼容性与命名清理。

## 9. 删除后必须检查的连带引用

- Python 的直接导入、包导出、共享测试夹具和测试替身。
- Hydra `defaults`、嵌套 `_target_`、实验覆盖、路径插值及回调监控指标。
- 动态模型清单、缩小测试配置函数、特定 Batch 分支和恢复断言。
- 训练、评估、分析与调度脚本中的论文实验名和硬编码路径。
- 环境清单、锁文件、CI 的依赖安装和测试命令；保留的 import 决定依赖，不仅看目录名字。
- 文档里的“已支持”“已验证”、文件链接、论文标题、旧仓库名和本机路径。

可用文件搜索和文本搜索找线索，但字符串搜索无命中不代表语义上已解耦。最终以导入、配置实例化和实际测试为准。

当前默认模型是 MNIST 相关配置，公共测试夹具包含语音导入。因此“删掉 VC 文件夹后运行现有命令”不是可接受的提取流程。

## 10. 新仓库验收清单

以下项目均是待在新仓库执行的验收，不是本文已执行结果。

- [ ] 最小环境下可导入生产模块并收集测试，不要求语音或其他已移除任务的依赖。
- [ ] 默认 CPU 示例可离线完成训练、验证、测试和预测，无隐式下载。
- [ ] 保留的每个模型/实验配置都能实例化；不存在指向已删除类的 `_target_`。
