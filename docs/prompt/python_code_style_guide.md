# Python 代码组织与注释规范

> 适用范围：Python 模块、类、函数，以及训练脚本、数据处理、服务端和 Agent 等项目代码。\
> 核心目标：**结构清晰、入口明确、职责分离、中文注释适度、便于自顶向下阅读。**

## 1. 总体原则

本规范**只有一套**，不区分“类模板”和“非类模板”。模块、类和复杂函数都按照相同的逻辑组织：

**职责说明 → 定义与状态 → 辅助能力 → 内部实现 → 核心流程 → 对外接口 → 可选入口**。

这是阅读和组织代码的**逻辑顺序**，而非必须逐项出现的固定语法结构。根据代码的真实职责选择合适分区，不为了套模板增加空函数、无意义包装层或重复注释。

具体要求：

1. **优先清晰的代码，注释作为补充。** 清楚的函数名、类型标注和简洁流程优先于长篇注释。
2. **从入口能够追踪主要调用路径。** 复杂模块可在模块 docstring 中给出简短的调用树；简单模块不需要。
3. **按职责而不是按形式分区。** 一个以类为核心的模块，可以直接把该类作为主要业务实现；数据类则归入定义区域。
4. **统一使用中文注释和中文 docstring。** 外部 API 名称、库名、术语以及已有项目约定可以保留英文。
5. **只对非显然的逻辑解释“为什么”。** 例如边界条件、状态变化、异常恢复、算法取舍、资源生命周期等。
6. **遵循现有工程规范。** 包括 PEP 8、类型标注、项目框架约定及既有代码风格；本规范不应破坏框架要求的函数签名或生命周期。

## 2. 统一的结构模型

| 逻辑分区                 | 作用                                       | 适用时机                 |
| ------------------------ | ------------------------------------------ | ------------------------ |
| Overview / 职责说明      | 说明当前代码单元的职责、主要能力及重要约束 | 模块、类、复杂函数       |
| Imports / 依赖导入       | 标准库、第三方库、项目内部依赖             | 模块级；不强制在类内重复 |
| Definitions / 定义与状态 | 常量、类型、配置、数据结构、必要的对象状态 | 有相应内容时             |
| Utilities / 辅助功能     | 校验、格式转换及低耦合工具                 | 有独立辅助能力时         |
| Internal / 内部实现      | 具体业务步骤、计算及处理细节               | 逻辑需要拆分时           |
| Core Logic / 核心流程    | 组织多个操作及阶段，体现执行顺序           | 存在值得单独表达的流程时 |
| Public API / 对外接口    | 对调用方暴露稳定能力                       | 有对外调用边界时         |
| Entry Point / 执行入口   | 命令行、脚本或框架入口                     | 存在独立运行入口时       |

**分区不是必填项。** 一个小函数不需要再拆成若干“步骤函数”；一个只定义数据类型的模块也不需要 Core Logic。类的 `__init__`、属性、公开方法及内部方法都按同一职责逻辑归类，无需另建一套规范。

## 3. 统一注释规则

### 3.1 模块 docstring

建议包含：**模块职责**；必要时增加**主要能力、核心流程、关键约束**。不需要列出每个函数，也不需要重复代码能清楚展示的内容。

### 3.2 类 docstring

简述类的职责、对外能力以及重要状态或生命周期约束。只有存在多阶段调用关系时才增加简短流程树。

### 3.3 函数 / 方法 docstring

- **简单函数**：一句中文说明即可。
- **对外函数、复杂函数**：根据实际情况描述参数、返回值、异常、重要副作用或约束。
- **无需机械补齐所有栏目**：不存在特殊异常或副作用时不写对应栏目。
- 类型已通过标注清晰表达时，注释着重解释**语义**，而非再次描述类型。

### 3.4 分区与行内注释

- 大型模块或类可使用 `# ===` / `# ---` 标记职责区域；简单代码不必使用。
- 核心流程可以使用 `# 1. ...`、`# 2. ...` 标记**确实有意义**的阶段；不必对每条赋值写注释。
- 注释应解释复杂条件、特殊处理、设计选择或约束，**避免翻译代码**。
- 修改行为时同步更新相关注释；不保留与实现不符的调用树和描述。

## 4. 统一参考示例

以下是**一份**包含类与模块级函数的示例，仅展示统一组织方法。实际代码应删去不需要的分区和方法，而不是完整照搬。

```python
"""任务处理模块：校验任务配置，处理输入数据，并返回结果。

主要能力：
    - Processor：封装可复用的数据处理逻辑与运行状态。
    - run：提供一次性任务执行入口。

核心调用路径：
    main() -> run() -> Processor.process()
                             ├── _validate()
                             └── _transform()
"""

# =============================================================================
# 1. Imports - 依赖导入
# =============================================================================

from dataclasses import dataclass
from typing import Sequence


# =============================================================================
# 2. Definitions - 配置、常量与类型
# =============================================================================

DEFAULT_FACTOR = 2


@dataclass(frozen=True)
class Config:
    """任务配置；factor 为每个输入元素的乘数。"""

    factor: int = DEFAULT_FACTOR


# =============================================================================
# 3. Core Components - 主要业务对象
# =============================================================================

class Processor:
    """处理整数序列，并记录已成功处理的元素数量。

    调用方式：创建实例后调用 process()；实例可重复使用。
    """

    # 初始化与状态
    def __init__(self, config: Config) -> None:
        """保存配置并初始化处理计数。"""
        self._config = config
        self._processed_count = 0

    @property
    def processed_count(self) -> int:
        """返回累计成功处理的元素数量。"""
        return self._processed_count

    # 辅助校验
    def _validate(self, data: Sequence[int]) -> None:
        """校验输入元素；类型不合法时抛出 TypeError。"""
        if any(type(item) is not int for item in data):
            raise TypeError("数据元素必须为整数")

    # 内部实现
    def _transform(self, value: int) -> int:
        """将单个整数乘以配置中的系数。"""
        return value * self._config.factor

    # 对外接口 / 核心流程
    def process(self, data: Sequence[int]) -> list[int]:
        """处理输入数据并返回新列表。

        参数：
            data: 待处理的整数序列。

        返回：
            转换后的新列表，不修改原始输入。

        说明：
            仅在整个处理成功后更新计数，避免失败时误计数。
        """
        self._validate(data)
        result = [self._transform(item) for item in data]
        self._processed_count += len(result)
        return result


# =============================================================================
# 4. Public API - 模块对外接口
# =============================================================================

def run(data: Sequence[int], config: Config | None = None) -> list[int]:
    """使用指定配置执行一次数据处理任务。"""
    processor = Processor(config if config is not None else Config())
    return processor.process(data)


# =============================================================================
# 5. Entry Point - 可选执行入口
# =============================================================================

def main() -> None:
    """运行简单示例。"""
    print(run([1, 2, 3]))


if __name__ == "__main__":
    main()
```

这段代码故意没有加入不必要的模块级 Utilities、Internal Functions 或 `_execute()` 包装函数。**结构要反映实际复杂度**。当模块变复杂时，可以在同一规范下进一步拆分为辅助功能、内部实现、核心编排等分区。

## 5. 实际应用的判断标准

- 一个函数一眼能理解：保留简短 docstring，不加大段注释。
- 函数存在多个重要阶段：使用清楚的阶段性注释；必要时提取内部函数。
- 一段逻辑被多处调用：考虑抽取辅助函数，而不是复制代码。
- 类封装明显的状态或生命周期：在类 docstring 中说明重要约束；无需列举每个字段。
- 核心算法或异常处理不直观：解释**原因、假设、边界和失败行为**。
- 代码单元很大：适当添加分区标题，便于定位；小型代码单元不强制分区。
- 已有框架（如 Hydra、Lightning、FastAPI）定义入口形式：保留框架入口，在其附近说明关键初始化、运行顺序和副作用。

## 6. 给 AI 的统一执行要求

生成、修改或重构 Python 代码时，遵守以下要求：

1. 使用**同一套**职责组织规则处理模块、类和函数，不为类和非类分别套用固定模板。
2. 根据代码复杂度选择需要的分区，不补齐不存在的部分。
3. 在模块或复杂类开头写简洁中文 docstring；执行链条较复杂时给出简短调用路径。
4. 对外接口和非简单函数使用中文 docstring，按需要说明参数、返回值、异常与重要副作用。
5. 仅在关键阶段、复杂分支、算法假设和非显然设计选择处添加注释，不逐行翻译代码。
6. 保持主流程清楚可追踪；只有职责划分有实际价值时才提取辅助函数。
7. 优先保留项目已有行为、接口、类型标注及框架约定；结构整理不应擅自改变逻辑。
8. 代码发生修改时，同步维护模块说明、调用路径和相关注释。

**验收标准：** 阅读者能够快速找到入口、理解职责、追踪调用路径、识别关键状态与约束；同时，代码中不存在为了符合模板而产生的冗余层级或重复注释。
